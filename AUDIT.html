Ready for public users?

Not until this branch is deployed: production still runs the old build, which has every issue listed below. Launch once these are done:

  1. Push backend_auth. On the server run npm run check:predeploy against production and fix what it flags (run migrateEventVendorIds if it reports bad vendor links).
  2. Run ./deploy.sh and apply the nginx files in the same window, then reload nginx.
  3. Regenerate review links for any event whose link was already shared (old links have no token).
  4. Make one real paid booking, check the ticket and email arrive, then refund it.

What was fixed

Grouped by area, most severe first. The code on the right is the commit to look at.

Second hardening pass 23

Found and fixed after 1650ae4, each with a regression test that fails on the old code. Most were found by the new automated checks: a route-auth matrix that calls every API route without login, and an ownership (IDOR) suite.

Security 12

  • Critical

    Account takeover through the legacy employee API

    PUT /api/employees/:id applied the whole request body, so a vendor could point their employee at any user (even an admin) and the handler then rewrote that user's login email. A password reset finished the takeover. The same hole let a vendor move an employee onto another vendor and read its attendees. Updates now use an allowlist and never touch the login email.

    b331903
  • High

    Public review link created accounts, fake bookings and certificates

    Anyone who knew an event id could create verified accounts, paid-looking registrations, reviews and certificates for any email, and learn account ids. The shared link now carries a secret token, never acts as an existing account unless that user logs in, and is rate limited. Offline attendees keep working; links shared before this change must be regenerated.

    cec47b8
  • High

    Ticket transfer brought used and refunded tickets back

    Transferring a ticket reset it to active with a fresh QR code, so a checked-in, cancelled or refunded ticket became valid again. Only active, unused tickets can be transferred now.

    00c810c
  • High

    Any vendor could read or issue tickets for other vendors' events

    Any vendor could list the tickets (attendee names and emails) of any order, and mint valid tickets for another vendor's event. Both are now limited to the event's own vendor and staff.

    3a4722d
  • High

    Vendors could issue certificates under other vendors' events

    Single and bulk certificate generation didn't check event ownership, so a vendor could issue official certificates under a competitor's event to any email.

    ff5c8ea
  • High

    Student signup could plant children on other accounts

    The public student-program form attached a child to any existing account by email and put the submitted text into the welcome email as raw HTML (phishing from our domain). Existing accounts now need their owner logged in, the email is escaped, the temporary password is cryptographically random, and the form is rate limited.

    7339006
  • High

    Scripts inside uploaded SVG images ran on the API domain

    Uploaded files are served from the API origin, so a script inside an uploaded SVG ran there when the file was opened directly. SVG/XML/HTML now get a sandboxing CSP (images and PDFs still display), and customer booking attachments no longer accept SVG.

    cb84b5c
  • Medium

    Certificate lookup exposed children's names to anyone

    Typing any email on the public certificate lookup showed the recipients' names, events and PDF links. Now only the logged-in owner sees the list; anyone else gets "check your inbox" and the list is emailed to that address.

    83a52fb
  • Medium

    Vendors could give themselves paid promotion and ratings

    Creating an event accepted isFeatured, premium promotion, featuredUntil and fake rating counts from the request. One shared protected-field list now covers create and update.

    4e703a8
  • Medium

    Search boxes accepted regular expressions

    76 search sites put raw text into database regex queries: typing "(" returned a 500, and crafted patterns could tie up the database. Searches now match the literal text.

    99dca63
  • Medium

    Public forms could be used to spam inboxes

    Contact, newsletter, partnership, lead and competition-draft forms only had the general rate limit. Each now allows 60 submissions an hour per network, and the event lead form validates its fields (a malformed name used to cause a 500).

    fcaf589
  • Medium

    Anyone could burn the paid exchange-rate quota

    POST /api/currency/refresh was public and called the paid FX API every time. It is now admin-only; nothing in the site used it.

    ba194e3

Payments 5

  • Critical

    One payment could confirm many orders and registrations

    Booking confirm only checked the amount, and registration confirm checked nothing, so one succeeded Stripe payment could be replayed to confirm other pending orders of the same price, or any number of paid registrations. Both now require the payment to be the one created for that record.

    1b60316
  • High

    Competition entries marked paid with someone else's payment

    Finalizing an AI Art Competition entry only checked that the Stripe session was paid, so one paid session could finalize unlimited free drafts. It must now be the session created for that entry.

    f1c03d8
  • High

    Late Stripe events could revive refunded orders

    With Stripe now retrying failed webhooks, a delayed "payment succeeded" could flip a refunded order back to paid, re-send confirmation emails and count the affiliate sale twice. Each is now guarded.

    9cd97de
  • High

    Paid competition entries lost when the tab was closed

    Only the browser's return trip finalized an entry, so a parent who paid and closed the tab kept an unpaid draft and no confirmation. The Stripe webhook now finalizes it too, exactly once.

    ababdd3
  • Medium

    Stale Stripe events could mislead customers or downgrade vendors

    A late "payment failed" event notified customers who had already paid, and an out-of-order subscription event could downgrade a paying vendor. Subscription and invoice errors were also swallowed, losing the update. Now: no notice for paid orders, the subscription's current state is read from Stripe, and failures make Stripe retry.

    1b823a8

  • Critical

    Vendors could list another vendor's ticket holders (customer names and contacts), claim any event, and read another event's cancellation contact list. Payments 4

  • Critical

    Paid orders cancelled by the seat-expiry sweep

    The 15-minute sweep cancelled every pending order without asking Stripe. If the confirmation was missed, a customer who paid lost their booking. It now checks Stripe first and confirms paid orders instead.

    6f29526
  • High

    Failed Stripe webhooks were never retried

    The webhook told Stripe "received" before processing and marked the event done up front, so a database blip lost the event. It now processes first and answers 500 on failure, so Stripe retries.

    1650ae4
  • High

    Pasted Stripe secret keys charged customers with no booking

    With a pasted key the payment is created on the vendor's own Stripe account, but confirmation looks it up on the platform account. Saving a pasted key is now blocked (409); Stripe Connect is unaffected.

    f3745b5
  • Medium

    Webhooks could be rate-limited

    Stripe webhooks counted toward the API rate limit, and Stripe retries on 429. Webhooks and health checks are now exempt, and the general limit rose from 100 to 600 per minute per IP.

    3789168
